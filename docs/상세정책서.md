# 루틴 체크 앱 상세 정책서 (v1)

## 1. 정책 목적
- 기획서를 개발 가능한 수준으로 구체화한다.
- 화면별 동작, 데이터 상태, 예외 처리 기준을 고정한다.

## 2. 도메인 모델 정책

## 2.1 Task
- 정의: 반복 수행할 단위 작업
- 필드
  - `id`
  - `title` (1~50자)
  - `category` (`운동`, `공부`, `생활`, `기타`)
  - `repeat_type` (`DAILY`, `WEEKLY_DAYS`)
  - `repeat_days` (요일 배열, `WEEKLY_DAYS`일 때 필수)
  - `start_date`
  - `is_active`
  - `memo` (선택)
  - `created_at`, `updated_at`

## 2.2 TaskLog
- 정의: 특정 날짜의 수행 기록
- 필드
  - `id`
  - `task_id`
  - `date` (로컬 날짜 기준)
  - `status` (`DONE`, `SKIPPED`, `PENDING`)
  - `started_at`
  - `ended_at`
  - `checked_at` (DONE/SKIPPED 시각)
  - `note` (선택)
- 제약
  - `task_id + date` 유니크

## 2.3 ReminderRule
- 정의: 지연 알림 규칙
- 필드
  - `id`
  - `trigger_task_id`
  - `delay_minutes` (최소 1분)
  - `message`
  - `is_active`
  - `created_at`, `updated_at`

## 2.4 ReminderEvent
- 정의: 실제 발송 스케줄 단위
- 필드
  - `id`
  - `rule_id`
  - `triggered_by_task_log_id`
  - `scheduled_at`
  - `sent_at`
  - `status` (`PENDING`, `SENT`, `CANCELED`, `FAILED`)
  - `repeat_interval_minutes` (선택)
  - `repeat_until` (선택)
  - `dismissed_at` (선택)

## 3. 반복 규칙 정책
- `DAILY`: 시작일 이후 모든 날짜에 노출
- `WEEKLY_DAYS`: 지정된 요일에만 노출
- 공통
  - `is_active=false`면 오늘 목록/알림 트리거 대상에서 제외
  - 과거 기록은 유지

## 4. 화면별 정책

## 4.1 홈(오늘)
- 표시 대상
  - 오늘 날짜에 해당하는 활성 Task
- 기본 정렬
  - 미완료(PENDING) 우선
  - 이후 생성순
- 행위
  - 완료 체크: `TaskLog.status = DONE`
  - 스킵 체크(선택 버튼): `TaskLog.status = SKIPPED`
  - 체크 해제: `PENDING`으로 복원
- 예외
  - 동일 날짜 중복 로그 생성 금지(업데이트 처리)

## 4.2 달력
- 월간 뷰에서 날짜별 표시
  - 완료율: `DONE / (DONE + SKIPPED + PENDING 대상수)`
- 날짜 선택 시
  - 해당일 테스크 목록과 상태 표시
  - 과거 날짜 상태 수정 허용 여부: 초기 버전 허용
- 예외
  - 존재하지 않는 과거 Task는 당시 기준으로 계산하지 않음(활성 이력 미관리 가정)

## 4.3 테스크 관리
- 생성
  - 제목 필수
  - 요일 반복 선택 시 최소 1개 요일 필수
- 수정
  - 반복 규칙 변경 시 미래 날짜부터 반영
- 삭제
  - 소프트 삭제(비활성화) 우선
  - 기존 TaskLog는 유지
  - 연결된 ReminderRule은 함께 비활성화
  - 연결된 pending ReminderEvent는 취소 처리

## 4.4 알림 설정
- 규칙 생성
  - 기준 테스크 필수
  - 지연 시간 필수
  - 지연 시간은 `시간 + 분` 입력으로 받되, 내부 저장은 분 단위
  - 메시지 기본값 제공
  - 반복 간격(분) 설정 가능
- 규칙 동작
  - 기준 테스크가 DONE 처리되는 시점에 `ReminderEvent` 생성
  - 알림 기준 시각은 해당 `TaskLog.ended_at`
  - 발송 시각 도달 시 `SENT`
- 취소 정책
  - 연결된 기준 Task가 비활성화되면 관련 pending 이벤트도 `CANCELED`

## 4.5 반복 리마인드 정책
- 목적: 특정 테스크 종료 이후 필요한 후속 확인의 누락을 줄인다.
- 예시
  - 출근 체크 완료 -> 9시간 후 퇴근 체크 알림
  - 알림 미해제 상태면 1분 간격 반복
- 공통 규칙
  - 최초 알림 시각은 `delay_minutes` 기준
  - 반복 알림은 `repeat_interval_minutes` 기준
  - 사용자가 알림을 수동 해제하면 반복 종료
  - 현재 버전은 `repeat_until` 범위 안에서 반복 재스케줄한다

## 5. 알림 동작 정책
- 타임존: 사용자 로컬 타임존(기본 Asia/Seoul)
- 중복 방지
  - 동일 `triggered_by_task_log_id + rule_id` 이벤트 1개만 허용
- 실패 처리
  - 발송 실패 시 `FAILED`
  - 초기 버전 재시도 없음(향후 확장)
- 알림 해제 처리
  - 사용자가 명시적으로 해제하면 `dismissed_at` 기록
  - 해제 이후 같은 이벤트의 반복 알림 생성 중단

## 6. 상태 전이 정책

## 6.1 TaskLog.status
- `PENDING -> DONE`
- `PENDING -> SKIPPED`
- `DONE -> PENDING`
- `SKIPPED -> PENDING`

## 6.2 ReminderEvent.status
- `PENDING -> SENT`
- `PENDING -> CANCELED`
- `PENDING -> FAILED`
- `SENT -> CANCELED`

## 7. 예외 처리 기준
- 제목 공백 입력: 저장 차단
- 반복 요일 미선택: 저장 차단
- 비활성 Task 체크 시도: 차단 후 안내
- 과거 날짜 대량 수정: 초기 버전 미지원

## 8. MVP 완료 기준
- 오늘 화면에서 3회 이내 조작으로 체크 완료 가능
- 달력에서 특정 날짜 기록 확인 가능
- 출근 체크 후 지연 알림이 정확히 1회 발송
- 중복 알림 이벤트 미발생

## 9. 테스트 시나리오
- 매일 반복 Task가 연속 7일 노출되는지 확인
- 월/수/금 Task가 해당 요일에만 노출되는지 확인
- 같은 날짜에서 체크/해제를 반복해도 로그 1건 유지 확인
- 출근 체크 후 N시간 알림 생성/발송 확인
- 퇴근 선완료 시 관련 알림 취소 확인

## 10. 오픈 이슈 (다음 버전 결정)
- SKIPPED를 완료율 분모에 포함할지 여부
- 알림 재시도 정책(FAILED 처리 이후)
- 태스크 이력 버전 관리 필요 여부
